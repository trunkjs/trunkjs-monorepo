# @trunkjs/api-stub

Create typed clients with `createApi<T>(routes, config)` or use the generated
API. Use `.request({ params, query, body })` for JSON, `.ndjson({ onLine })`
for streams, and `.raw()` for a native Response. Use `.with()` for scoped defaults.

## Application feedback

Configure one shared feedback/error integration at startup. In applications
use these callbacks rather than writing custom loading/error handling around
individual API calls or duplicating it in components. The stub does not
depend on a UI library; connect the callbacks to the application's presenter.

```ts
const API = generatedAPI.with({
  feedback: 'mini',
  onFeedbackStart: event => console.log('start', event.id, event.name),
  onFeedbackEnd: event => console.log('end', event.id, event.status),
  onError: event => console.error(event.name ?? event.context.name, event.error),
});

await API.User.Update.request({
  params: { userId: 42 },
  body: { name: 'Ada' },
  feedback: { name: 'Save user', successMessage: 'User saved.' },
});
```

The console callbacks illustrate where to connect the central UI adapter.
`feedback` accepts a key, `FeedbackDetails` (key, name, loadingMessage,
successMessage, errorMessage, data), or false. Defaults merge across
API, namespace, route and request. False disables start/end, while
`reportError: false` independently disables the global error callback.
Events share a unique invocation ID; end status is success/error/aborted.
The adapter manages concurrent active IDs and presentation. Errors still
reject; aborts do not trigger onError. A shared transport failure is reported
once per error callback. Raw HTTP statuses remain the caller's responsibility.
Do not add per-component catch blocks solely to display API errors.

Use `concurrency` for request coordination (queue, queue-latest, parallel,
reject, abort, join, join-full). See [README](README.md) for details.
