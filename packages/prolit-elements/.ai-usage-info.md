# AI usage info: @trunkjs/prolit-elements

## `tj-include`

Use `<tj-include>` to fetch an HTML fragment.

Immediate loading remains the default:

```html
<tj-include src="/fragments/details.html"></tj-include>
```

Use `lazy` when the request should start only once the element becomes visible. Lazy loading uses `IntersectionObserver` and falls back to immediate loading where it is unavailable.

```html
<tj-include src="/fragments/details.html" lazy></tj-include>
```

While a request is active, the host reflects the `loading` attribute and dispatches `loadstart`. Successful loads dispatch `load`; failures dispatch `error`.

A custom loader can be supplied as a direct child marked `slot="loader"`. This is intentionally a declarative marker even though `tj-include` remains a light-DOM component, so arbitrary loading components can be used.

```html
<tj-include src="/fragments/details.html" lazy>
  <my-spinner slot="loader"></my-spinner>
</tj-include>
```

Without a custom loader, `tj-include` creates a simple text loader. Its text can be configured with the inherited CSS custom property `--tj-include-loader-text`:

```css
tj-include {
  --tj-include-loader-text: 'Loading details…';
}
```

Use `unwrap` when the fetched nodes must become siblings at the location of the include rather than children of the `tj-include` host:

```html
<section>
  <tj-include src="/fragments/details.html" lazy unwrap></tj-include>
</section>
```

After a successful load, this becomes conceptually:

```html
<section>
  <!-- fetched fragment nodes directly here -->
</section>
```

`unwrap` is useful for parent components that classify or project their direct light-DOM children. Do not use `unwrap` when code needs to retain the `tj-include` element after loading.
